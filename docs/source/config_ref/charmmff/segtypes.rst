``segtypes``
------------



How the file set is decided
^^^^^^^^^^^^^^^^^^^^^^^^^^^

There is one list, ``files``, and its order is the order the files are loaded
in.  That matters twice over, and nothing downstream reports either:

* psfgen gives a residue the ``DEFA FIRS ... LAST ...`` in force when that
  residue's *definition* is read, so topology order fixes terminal patches.
* Parameter merging is last-wins (CHARMM's ``READ PARAM APPEND``), so a term
  defined in two files takes its value from the later one.

To **add** a file -- another stream from the CHARMM release, or your own
CGenFF stream for a ligand -- name it in ``files``:

.. code-block:: yaml

  charmmff:
    searchpath:
      - ~/my-cgenff
    files:
      - toppar_all36_lipid_sphingo.str   # from the CHARMM release
      - myligand.str                     # from ~/my-cgenff

Release files and your own files go in the same list; pestifer resolves each
basename against the release tree and your ``searchpath`` directories alike.

To **replace** pestifer's default set entirely, set ``replace_defaults: true``
and list every file you want:

.. code-block:: yaml

  charmmff:
    replace_defaults: true
    files:
      - top_all36_prot.rtf
      - par_all36m_prot.prm
      - toppar_water_ions.str

Added files load *after* the defaults, which includes pestifer's own
``toppar_pestifer_conflict_resolutions.prm``.  A parameter you supply
therefore overrides one pestifer has deliberately arbitrated -- the right
reading of an explicit request, but worth knowing you have it.

Deprecated: ``standard``, ``custom`` and ``user_custom``
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

These three groups named a file's *provenance* where what a user needed to
express was *intent*, and are retained only so existing configs keep working.
Entries in any of them are folded into ``files`` with a warning;
``user_custom.searchpath`` and ``user_custom.segtypes`` become ``searchpath``
and ``segtypes``.
